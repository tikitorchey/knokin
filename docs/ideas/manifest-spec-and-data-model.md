# Knokin Turn Table manifest仕様・データモデル(たたき台)

Oct 9, 2026 · @Tiki Torchey

## 目的とスコープ

本仕様は、撮影(Blender)・パッキング・ビューアの三者が共有するデータ契約として、骨組み上のプリレンダー画像群を記述する manifest と画像配置を定義する。

**対象**

- 座標規約(θ・φの基準、回転方向)
- 骨組みグラフ(ノード・エッジ)
- フレーム参照(画像の置き場所と命名)
- 撮影メタデータ(再現性のための記録)
- ビューア側の移動ロジックの振る舞い(描画から切り離した純関数)

**対象外(Day2以降)**

- 圧縮方式の選定と最適化(Day1は独立画像連番のみ)
- ライティング変更、アニメーション、ズームの可変化、深度・補間

**設計原則**

1. 実装非依存: Blender・Chrome・将来のネイティブで同じ manifest を読む。
2. フレーム参照の抽象化: 画像連番から動画セグメントへ、manifest の差し替えだけで移れる。
3. 交点の共有: 交点の画像は全エッジで1枚を共有し、保存も1枚にする。
4. バージョン付与: `schema` に版を入れ、後方互換を判定できるようにする。

**前提(確定済み)**: 独立した研究開発。ターゲットは Chrome(PC と Android)。本番のネイティブ化は性能不足の場合の選択肢として残す。

**骨組みとカメラの方針(確定)**: データモデルが持つのは、ノードとエッジのグラフだけ。緯線・経線の格子は、アドオンがグラフを生成するプリセットの一つとして扱い、仕様には含めない。カメラ条件(解像度・画角・距離・回転中心)は作品ごとに manifest で宣言し、作品内の全フレームで固定する。試作は均一格子のプリセットだけを実装する。

## 座標規約

Blender の世界座標(Z上向き・右手系)に合わせ、被写体を原点に固定してカメラが球面上を周回する。以下は提案であり、確定は未決事項で行う。

| 項目 | 規約(提案) |
| --- | --- |
| 単位 | 度(°)。manifest 内の角度はすべて度 |
| θ(方位角) | カメラが -Y 側にある位置を 0°。+Z軸の上から見て反時計回りを正。範囲は \[0, 360) の周期 |
| φ(仰角) | 水平を 0°、上方向を正。範囲は \[-90, 90\]。ただし極付近は使わない(下記) |
| カメラ位置 | 方向ベクトル d = (cosφ·sinθ, −cosφ·cosθ, sinφ) に距離 R を掛け、回転中心 pivot を足した点 |
| カメラ姿勢 | 常に原点を向く。ロール 0(上方向は +Z) |
| カメラ内部パラメータ | 作品ごとに manifest の camera で宣言する(既定値はアドオンのプリセット)。同一作品の全フレームでは固定 |
| ライティング | ワールド座標に固定。全フレームで同一 |

**検算**: θ=90°, φ=0° のとき d=(1, 0, 0)。カメラは被写体の右手側(+X)に回り込む。

**極の扱い**: φ=±90° では θ が縮退する。骨組みは φ の使用範囲を ±75° 以内(斜めを含む構成は ±60°)に制限し、極そのものはフレームに含めない。

**ビューアの入力規約(提案)**: 右ドラッグで被写体が右へ回る(θ が減少)。下ドラッグで上から覗き込む(φ が増加)。この向きはビューア側の設定で、manifest には含めない。

## 骨組みグラフ

骨組みは、ノード(交点)とエッジ(ノード間をつなぐ連番)だけで表す。セルや緯線・経線という概念はグラフには持ち込まず、エッジの種別ラベルに留める。

| 要素 | 持つ情報 | 備考 |
| --- | --- | --- |
| ノード | id, θ, φ | 画像を1枚持つ。複数のエッジが共有する |
| エッジ | id, kind, from, to, delta(Δθ, Δφ), frames | 端点を含むフレーム数。frames−1 区間で等分 |
| kind | 自由なラベル(格子プリセットでは lat, lon, diag) | ビューアの挙動には影響しない。オーサリングと検証用 |

**エッジの規則**

- フレーム 0 は from ノードの画像、フレーム frames−1 は to ノードの画像。この2枚はエッジ側に保存せず、ノード画像を参照する。
- 途中の角度は、from の (θ, φ) に delta を (i / (frames−1)) 倍して足したもの。緯線が θ=360° をまたぐ場合も delta が向きを一意に決めるので、曖昧にならない。
- エッジは双方向。to から from へ進むときは、フレームを逆順に読む。
- 斜めエッジも同じ形式。1区間あたりの角度差は (Δθ, Δφ)/(frames−1) で、1°刻みの辺より大きくなる。

**格子の扱い**

格子(緯線・経線・斜め)は、アドオンが骨組みグラフを生成するプリセットであり、データモデルの一部ではない。ビューアは `delta` と `frames` だけでグラフを扱い、格子を前提にしない。試作では均一格子のみを実装する。θ と φ の間隔を同じにすると、斜めの角度差が揃う。例えば 30° 格子・φ ±60° なら、緯線 5 本・経線 12 本で、斜めは 1 区間 (1°, 1°) で進む。重点エリアの密度変更は、グラフ生成側の機能として後から足す。

**ノードの次数**: 緯線・経線のみなら 4、×(斜め2本)を足すと 8。×の中心点もノードとして共有する。

## フレーム参照とコンテナ

ビューアは画像のファイル名を直接組み立てず、「ノード n の画像」「エッジ e の i 番目」という論理参照を `resolve` に渡して取得する。圧縮方式を変えても、ビューアの移動ロジックは変わらない。

```text
turntable/
  manifest.json
  frames/
    n/n000.avif          ノード画像
    e/e0001/0001.avif    エッジの途中フレーム(端点は含まない)
    e/e0001/0002.avif
```

| 論理参照 | 意味 | Day1 の解決先 |
| --- | --- | --- |
| node(n) | ノード n の画像 | `frames/n/{n}.avif` |
| edge(e, i) | エッジ e の途中フレーム i(1 ≦ i ≦ frames−2) | `frames/e/{e}/{i:04d}.avif` |

端点(i=0 と i=frames−1)は node(from)・node(to) に解決する。ビューア側では、エッジ上の位置 t から参照への変換を `frameRef(edge, i)` に一本化する。

**コンテナ**

- 開発中: フォルダのまま、ローカルサーバーまたは File System Access API / OPFS で読む。
- 配布時: 無圧縮(store)の zip、または HTTP Range で個別取得できる単一ファイル。画像はすでに圧縮済みなので、zip での再圧縮は意味がない。

**画像仕様(Day1)**

- AVIF(アルファ付き)を第一候補、WebP を比較用とする。全フレームで解像度・色空間(sRGB)・形式を揃える。
- アルファはプリマルチプライドを採用する(決定ログ D02)。撮影側とビューア側で同じ扱いに統一する。

**将来の差し替え**: `frames.codec` に `image-seq`(Day1)を入れる。動画セグメントに移る場合は、別の codec 名と、エッジ単位のセグメント参照を追加する。ノードのキーフレーム性は、この構造にすでに含まれている。

## manifest.json スキーマ案

下の例は、ノード3つ・エッジ3本の最小構成。実際のファイルは、撮影アドオンが骨組み設定から自動生成する。

```json
{
  "schema": "knokin-turntable/0",
  "meta": {
    "title": "sample",
    "created": "2026-10-09",
    "generator": "blender-addon/0.0.1"
  },
  "coords": {
    "unit": "deg",
    "up": "+Z",
    "thetaZero": "camera-at -Y",
    "thetaDir": "ccw-from-above",
    "phiDir": "up-positive"
  },
  "camera": {
    "projection": "perspective",
    "focalMm": 85,
    "sensorWidthMm": 36,
    "distance": 3.0,
    "pivot": [0, 0, 0.9]
  },
  "image": { "width": 1920, "height": 1080, "alpha": "premultiplied", "colorSpace": "sRGB" },
  "frames": {
    "codec": "image-seq",
    "format": "avif",
    "base": "frames/",
    "node": "n/{node}.avif",
    "edge": "e/{edge}/{i:04d}.avif"
  },
  "nodes": [
    { "id": "n000", "theta": 0,  "phi": 0 },
    { "id": "n001", "theta": 30, "phi": 0 },
    { "id": "n002", "theta": 0,  "phi": 30 }
  ],
  "edges": [
    { "id": "e0001", "kind": "lat",  "from": "n000", "to": "n001", "delta": [30, 0],  "frames": 31 },
    { "id": "e0002", "kind": "lon",  "from": "n000", "to": "n002", "delta": [0, 30],  "frames": 31 },
    { "id": "e0003", "kind": "diag", "from": "n002", "to": "n001", "delta": [30, -30], "frames": 31 }
  ],
  "start": { "node": "n000" },
  "render": {
    "graphPreset": { "type": "uniform-grid", "cellDeg": 30, "phiRange": [-60, 60], "stepDeg": 1, "diagonals": "alternate" }
  }
}
```

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| schema | ○ | 仕様名と版。版が合わなければビューアは読み込みを拒否する |
| coords | ○ | 座標規約の宣言。規約を変えた場合に気づけるよう、値を明記する |
| image | ○ | 解像度・アルファ・色空間と、camera(投影・画角・距離・回転中心)。作品ごとに宣言し、作品内の全フレームで同一 |
| frames | ○ | 画像の配置規則と形式。`codec` で圧縮方式を切り替える |
| nodes / edges | ○ | 骨組みグラフ。`delta` は Δθ, Δφ、`frames` は端点を含む枚数 |
| start | ○ | 初期表示のノード |
| meta | 任意 | タイトル、作成日、生成ツール |
| render | 任意 | 撮影条件の記録(次章) |

## ビューア側の純関数仕様

操作感の核になる3つの関数を、DOM・描画・通信に触れない純関数として定義する。Web で確定させた挙動は、そのままネイティブ移植時の仕様書になる。入力は manifest から作った骨組みグラフと、現在の状態だけ。

```ts
type Pos =
  | { at: 'node'; node: string }
  | { at: 'edge'; edge: string; t: number }   // t は 0..frames-1 の実数

// ドラッグ量(画面上の dx, dy)を受け取り、新しい位置を返す
move(graph: Graph, pos: Pos, drag: { dx: number; dy: number }, opt: MoveOpt): Pos

// 位置から表示すべきフレームの論理参照を返す(最寄りの整数フレーム)
frameAt(graph: Graph, pos: Pos): FrameRef

// 進行方向に応じて先読みすべき参照を優先度順に返す
prefetch(graph: Graph, pos: Pos, heading: Heading, budget: number): FrameRef[]
```

**move の規則(提案)**

1. **エッジ上**: ドラッグ方向をエッジの接線方向へ射影し、その成分だけ t を進める。角度の換算では θ 方向に cosφ を掛け、高緯度でも画面上の動きと釣り合うようにする。
2. **端点に到達**: t が端のとき、ドラッグ方向と各接続エッジの方向の一致度(画面上の角度)を比べ、最も近いエッジを選ぶ。一致度が閾値(例: 45°)を超えるときは、その場に留まる(不感帯)。
3. **曲がりの粘り**: 直前に進んでいたエッジを優先する(ヒステリシス)。曲がるには、ドラッグ量が一定の距離を超える必要がある。
4. **行き止まり**: φ の端にあたるノードでは、外向きのエッジがないので、t を端に固定する。
5. **最寄り線への吸着**: ドラッグが斜めなら、規則 1 の射影で自然に最寄りのエッジへ寄る。セルの内側へは入れない。

**frameAt**: t を四捨五入して整数フレームを選ぶ。クロスフェードは Day1 では行わず、切り替えのみ(二重写りの有無は実機で判断する)。

**prefetch の方針**

- 現在のエッジの進行方向に、数フレームから十数フレームを先読みする。
- 端点が近づいたら、そのノードに接続する各エッジの先頭数フレームも先読みする。これで曲がった直後に待たされない。
- ドラッグ速度が速いほど、先読みの範囲を広げる。

**検証**: 純関数なので、「この位置から、このドラッグを与えたら、この位置になる」というテストケースを JSON で持てる。ネイティブ移植時は、同じケースを通すことで挙動の一致を確認できる。

**閾値・感度**(不感帯の角度、粘りの距離、感度)は `MoveOpt` で外から与える。Day1 の試作で、触りながら決める。

## 撮影メタデータと再現性

撮り直しは全枚に影響するため、「どの条件で撮ったか」を manifest の `render` に残し、同じ条件で再現できるようにする。

| 項目 | 記録する内容 | 目的 |
| --- | --- | --- |
| 環境 | Blender の版、レンダリングエンジン、GPU/CPU の別 | 差異の切り分け |
| 品質 | サンプル数、デノイザー(種類と設定)、ライトパス設定 | 全フレームで品質を揃える |
| シード | 全フレーム共通の固定値 | ノイズの不整合を防ぐ |
| シーン | .blend ファイルのハッシュ、ライティング設定のハッシュ | 条件変更の検知 |
| カメラ | 焦点距離、センサー、距離 R | 全フレームで固定した証跡 |
| 骨組み設定 | 格子間隔、φ の範囲、刻み幅、斜めの有無(生成プリセットの記録。ビューアは参照しない) | 骨組みの再生成 |
| フレーム検証 | 各フレームのハッシュ(任意。別ファイルでも可) | 欠落・破損の検出 |

**交点の共有規則**

- ノード画像は1回だけ撮り、接続する全エッジが参照する。エッジ側で撮り直さない。
- エッジの途中フレームは、ノードと同じシード・同じデノイズ設定で撮る。ノードと途中フレームで画質の質感が変わると、交点を通るときにチラつく。

**要検証**: シードを全フレームで固定すると、ノイズの模様が画面に張り付いて見える可能性がある(汚れた窓ごしに見るような現象)。一方、フレームごとにシードを変えるとチラつく。サンプル数を十分に取ってデノイズに任せる、固定シードで見え方を確かめる、のどちらが良いかを、Day1 の実測で決める。

## 決定ログ(品質最大方針)

試作段階の意思決定は、「作品のクオリティが最も高くなる選択肢」を採択する。ただし各決定には、手戻りの範囲と実用化での妥協余地をタグで残し、後から見直す分岐点がすぐ分かるようにする。

**タグの凡例**

- 手戻り `撮り直し`: 変更すると全枚(または大半)を撮り直す
- 手戻り `追加撮影`: 足す分だけ撮ればよい
- 手戻り `再派生`: マスターから派生物を作り直すだけ
- 手戻り `ビューア`: ビューア・パッカー側だけで吸収できる
- 妥協余地 `大` / `中` / `小` / `不可`: 実用化で品質を下げて、コストを削れる度合い

| ID | 論点 | 採択(試作) | 手戻り | 妥協余地 | 実用化での妥協案 |
| --- | --- | --- | --- | --- | --- |
| D01 | マスターの形式 | EXR 16bit float・リニア・RGBA。ビュー変換は焼き込まない | `撮り直し` | `大` | 8bit PNG、ビュー変換済み |
| D02 | アルファの扱い | プリマルチプライド(Blender の EXR に合わせる)。配信形式での対応は Day2 で検証 | `再派生` | `中` | ストレートへ変換 |
| D03 | 背景と影 | 背景は透過。接地影は影キャッチャーを別レイヤーで保存(作品が必要な場合のみ) | `撮り直し` | `中` | 影を合成して1枚にする、または影なし |
| D04 | シミュレーション | 全フレームで同一時刻に固定し、ベイク済みキャッシュで撮る | `撮り直し` | `不可` | なし(方式の前提) |
| D05 | 解像度 | マスターと配信は同一解像度。値は作品ごとに image で宣言する(クリエイターが決める)。ズームは解像度ではなく、カメラ軌道の拡張で扱う | `撮り直し` | `中` | 解像度を下げる(時間・容量が減る) |
| D06 | 骨組みの構成 | 30° 格子・φ ±60°・×(斜め2本)で 8 方向 | `追加撮影` | `大` | 斜め1本、または斜めなし |
| D07 | 刻み幅 | 1° | `撮り直し` | `大` | 2° に粗くする(絶対番地方式を入れれば、後から間を追加撮影できる) |
| D08 | 低解像度ノード画像 | v0 に含める(初期表示と先読み用) | `再派生` | `大` | 省略 |
| D09 | θ=0 の基準・入力規約 | 仮置きを維持(カメラが -Y 側、右ドラッグで θ 減少) | `ビューア` | `大` | 品質に影響しないので、後から変更可 |
| D10 | デノイズとシード | テスト撮影で決める。基準は、チラつきとノイズの張り付きが少ない方 | `撮り直し` | `小` | 要実測 |
| D11 | アドオンの運用要件 | 中断からの再開、欠落フレームの検出、フレームごとのハッシュを必須にする | なし | `不可` | なし(数百時間級のジョブの前提) |

**この方針で増えるコストの目安**(概算、未実測)

D06・D07 を同時に採ると、撮影時間と容量が重くなる。概算(1080p・1枚1分の仮置き)では、×構成は約 6,400 枚・約 107 時間。1枚あたりの時間と容量は解像度とサンプル数で大きく変わるため、テスト撮影の約100枚で必ず実測する。

実測の結果、試作として重すぎる場合は、手戻りの小さい項目(D06 の斜めの本数、D07 の刻み幅)から段階的に撮る案を検討する。
