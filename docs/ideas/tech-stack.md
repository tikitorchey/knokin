# Knokin Turn Table 技術構成(草案)

Oct 10, 2026 · @Tiki Torchey

## 位置づけ

試作に必要な最小限の4システム(撮影アドオン、パッカー、ビューア、フォーマット仕様)の技術構成をまとめた草案。具体的な設計は、リポジトリを作成し、実装しながら詰める。

計測・検証は独立したシステムにせず、ビューア(計測)・アドオン(撮影時間のログと骨組みの検証)・パッカー(容量のログ)に同梱する。

データの流れ:

1. アドオン: EXR マスターと manifest を出力
2. パッカー: AVIF 連番と低解像度ノード画像を派生し、manifest と画像群にまとめる
3. ビューア: manifest と画像群を読み、閲覧する

**試作から外すもの**

- 圧縮方式の探索(動画コーデック、アルファ分離): Day2
- 重点エリアのオーサリング(密度展開、T字接続): 後続
- 配布まわり(ストレージ、共有、埋め込み、ギャラリー): 後続。ローカル運用で足りる
- プレミアム機能との連携: 対象外

## 技術構成の一覧

実装言語は Python(アドオン・パッカー)と TypeScript(ビューア)の2つ。

| システム | 言語 | 主なライブラリ・ツール | 実行環境 |
| --- | --- | --- | --- |
| 撮影アドオン | Python(bpy) | 標準ライブラリのみ。bpy 非依存のコアと Blender 層に二分 | Blender の最新安定版(本撮影前に固定)。ヘッドレス中心 |
| パッカー | Python(CLI) | OpenImageIO(EXR 読み込み・縮小)、NumPy、avifenc(外部コマンド)、concurrent.futures | アドオンと同じマシン。基本は撮影後に実行 |
| ビューア | TypeScript | Vite、Vitest、Canvas 2D、createImageBitmap(ImageDecoder は比較)、Pointer Events | Chrome(PC と Android 実機) |
| フォーマット仕様 | JSON(manifest) | schema フィールドで版管理 | 三者の共有契約 |

## 撮影アドオンの方針

アドオンは Python のみで書き、bpy に依存しないコアと、bpy を呼ぶ薄い Blender 層に分ける。

| 層 | 内容 | bpy |
| --- | --- | --- |
| コア | 骨組みグラフ生成、検証、角度からカメラ位置への計算(座標規約の式)、manifest 出力、ジョブ状態管理 | 不要 |
| Blender 層 | カメラ配置、レンダリング、EXR 保存、最小限の UI パネル | 必要 |

- **分ける理由**: コアは pytest で単体テストできる(θ=90°, φ=0° → +X の検算も自動化)。撮影前の骨組み検証も単体で走る。標準ライブラリだけで済み、Blender 同梱 Python への pip 導入が要らない。
- **運用**: 数百時間級のジョブなのでヘッドレス(`blender -b file.blend -P ...`)が中心。GUI は設定とテスト撮影用の最小パネルに留める。
- **Blender の版**: その時点の最新の安定版(LTS には限定しない)を採用し、本撮影の開始前に固定して manifest の `render` に記録する。テスト撮影も同じ版で行い、撮影の途中では版を上げない。版が変わると描画結果がわずかに変わり、交点でチラつく可能性がある。
- **レンダリング**: フレームごとにカメラだけ動かして `render` を呼ぶ。Cycles の `use_persistent_data` でシーンの再構築を避けられる見込み(要実測)。
- **マスター保存**: EXR 16bit float・RGBA・ロスレス圧縮(ZIP など)。DWAA は非可逆なので避ける。
- **中断再開と欠落検出**: フレームごとに1行の JSONL ログ(ID、所要時間、サイズ、SHA-256)を追記する。保存は一時ファイルに書いてからリネームし、書きかけを残さない。再開時はログと実ファイルを突き合わせる。
- **設定ファイル**: 骨組み設定は JSON で、manifest の `render.graphPreset` と同じ形にする。
- **シードとデノイズ**: シーン設定から固定値を一括適用し、値は manifest に記録する。方針は D10 のテスト撮影で決める。
- **見送り**: 複数プロセスへのジョブ分割、GUI の作り込み。

## パッカーの方針

パッカーは Blender の外で動く Python の CLI で、マスターを読み、AVIF 連番と低解像度ノード画像を作る。

- **AVIF エンコード**: `avifenc` を外部コマンドで呼ぶ方式で開始する。品質・速度・色空間のパラメータを調整しやすい。Pillow の AVIF プラグインは、問題が出たときの代替とする。
- **EXR 読み込みと縮小**: OpenImageIO。色変換(リニアから sRGB、プリマルチプライドの扱い)は NumPy。
- **並列化**: `concurrent.futures` のプロセスプール。ただし撮影中は GPU/CPU を占有するので、基本は撮影後に実行する。テスト撮影の約100枚は並走しても問題ない。
- **コアの共有**: manifest の読み書き、骨組みグラフ、論理参照の解決(`resolve`)は、アドオンのコアと同じ Python モジュールにする。仕様の解釈が二箇所に分かれるのを防ぐ。
- **アルファ**: マスターはプリマルチプライド。AVIF 側の扱い(プリマルチプライド指定の有無)を最初に実測で確認する。誤ると縁に暗い輪郭が出る。
- **再現性**: 派生物ごとのエンコード設定(品質、速度、色空間)を manifest に記録する。
- **冪等性**: 入力ハッシュと設定が同じなら再生成しない。中断しても続きから走る。
- **検証**: 出力後に、manifest が参照するファイルがすべて存在するかを突き合わせる。
- **見送り**: 動画コーデックへの変換(Day2)、zip や HTTP Range 向けの単一ファイル化(配布まわり)。

## ビューアの方針

ビューアは Chrome(PC と Android 実機)向けの TypeScript で、描画から切り離した純関数を核にする。

- **構成**: 純関数(`move` / `frameAt` / `prefetch`)は DOM に触れない独立パッケージ。描画・入力・通信の層と分ける。
- **ビルド**: Vite。テストは Vitest で、純関数のテストケース(JSON)を読み込んで流す。
- **描画**: Canvas 2D で開始する。描画層は `show(bitmap)` 程度の小さなインターフェースに隔離し、WebGL へ差し替えられる形にする。クロスフェードは Day1 では行わない。
- **デコード**: `createImageBitmap` を基本とし、`ImageDecoder` は比較して選ぶ。デコードは先読みの段階で済ませる。Day1 はメインスレッドで始め、カクつけば Worker へ移す。
- **ストレージ**: ローカルサーバーからの取得を基本とする。大量フレームの再利用が必要になれば OPFS を足す。
- **入力**: Pointer Events でマウスとタッチを一本化する。感度・不感帯・粘りは `MoveOpt` として、デバッグ画面のスライダーで調整できるようにする。
- **メモリ管理**: デコード済みの `ImageBitmap` は 1080p の RGBA で約8MB/枚。先読みの枚数に上限を設け、範囲外は `close()` で解放する。上限は Android 実機で実測して決める。
- **計測の同梱**: デバッグオーバーレイ(デコード時間、メモリ、切替遅延、先読みヒット率)と計測ログの書き出し、純関数のテストランナー。
- **manifest**: `schema` の版を確認し、合わなければ読み込みを拒否する。
- **実機確認**: PC で動かしたビルドを、同一ネットワークから Android Chrome で開く。
- **見送り**: クロスフェード、WebGL 描画、動画セグメントの再生、iOS/Safari 対応。

## システム間の共有

Python 側はコードを共有し、Python と TypeScript の間は共通の正解データで一致を確かめる。

| 範囲 | 共有の方法 |
| --- | --- |
| アドオンとパッカー(Python) | manifest の読み書き、骨組みグラフ、`resolve` を同じ Python モジュールにする |
| Python と TypeScript | コードは共有できない。manifest のサンプルとテストケース JSON を共通の正解データにして、両側で検証する |

Python 側は骨組み生成と `resolve`、TypeScript 側は `move` と `frameAt` を、同じ manifest で検証する。純関数のテストケースは「この位置から、このドラッグを与えたら、この位置になる」を JSON で持ち、ネイティブ移植時にも同じケースを通して挙動の一致を確認できる。

## WebGL への切り替え条件とビルドツール

Day1 は Canvas 2D のままにし、次のいずれかが実測で必要になったら WebGL に差し替える。1枚を切り替えて表示するだけなら、Canvas 2D の `drawImage`(GPU 処理)で WebGL の利点はほぼない。

- クロスフェードが必要になった
- 影キャッチャーなど、複数レイヤーの合成が必要になった
- ズームの画質が不足した
- Android で `drawImage` が遅い

判断材料は、ビューアの計測オーバーレイにある切替遅延で取る。

**WebGL のデメリット(採用時の注意)**

- テクスチャのアップロードがメインスレッドを塞ぎ、モバイルでカクつく可能性がある
- GPU メモリが増える(ImageBitmap とテクスチャの二重保持になりやすい)
- Android でのコンテキストロストに備える必要がある
- アルファの扱いで縁に暗い輪郭が出やすい

**ビルドツール**

Vite を採用する。純関数パッケージを `tsc` だけでビルドできる形にしておけば、バンドラなしの最小構成など他の選択肢へ移る費用は小さい。
