# 実測の記録

規模の落とし方と、測れていないものは [test-strategy.md](test-strategy.md)。生データは [measurements/](measurements/)(JSON)。

**読む前に**: 数値はすべて単純な合成テストシーン(`python/tools/make_test_scene.py`)と **CPU 4コア・GPUなし・デスクトップ headless Chromium** での値。実作品・GPU・Android 実機では変わる。「この環境で言えること」と「実機/実作品で再測定が要ること」を分けて書く。

## 1. 座標(DD40)

Blender 実カメラ(`place_camera` → Cycles)で非対称シーンを8視点描画し、目視で仕様どおりと確認した(`measurements/coord-check.png`)。

| 視点 | 見えたもの | 仕様 |
| --- | --- | --- |
| θ=0, φ=0 | 黄の鼻が手前、赤い腕(+X)が右 | カメラは -Y 側 ✓ |
| θ=90, φ=0 | 白い先端(+X腕)が手前、緑の腕(+Y)が右 | カメラは +X 側 ✓ |
| θ=180 | 緑(+Y)が手前、赤が左 | +Y 側 ✓ |
| θ=270 | 鼻が右 | -X 側 ✓ |
| φ=+45 / -45 | 見下ろし / 見上げ(青い柱の傾きが反転) | 上が正 ✓ |

**影キャッチャー(DD36)**: 地面にシャドウキャッチャーを置くと φ≥0 では接地影が出るが、φ<0(カメラが地面の下)では被写体が消えて画像が空になる(`coord-check-shadow-catcher.png` の下段右2枚)。φ±60° を使う本構成とは両立しないので使わない。

## 2. 撮影

### 2.1 本番グラフからの100枚抽出(`--test-shoot 100`、1920×1080、32spp、OIDN、persistent、seed fixed)

シーン: 基本テストシーン(被写体は画面の約10%)。CPU 4コア。

| 項目 | 値 |
| --- | --- |
| 1枚あたり(初回除く平均 / 中央値 / 範囲) | 15.75 s / 15.89 s / 14.25〜19.70 s(初回 19.70 s) |
| EXR(16bit half RGBA, ZIP) | 平均 519 KB(423〜624 KB) |
| 5,928枚へ換算 | **約 25.9 時間、EXR 約 3.1 GB**(このシーン・この CPU) |

重いシーン(`--busy`: 画面の約33%を占める高周波テクスチャ、同条件12枚): 約 30 s/枚、EXR 約 2.27 MB → 5,928枚で約 49 時間、約 13.5 GB。**実作品の撮影時間・容量はシーンで大きく変わる**ので、実作品での再測定が必要(手順: `--test-shoot 100`)。

### 2.2 サンプル数とデノイズ(同じ12枚を全条件で撮影し、512spp デノイズ済みを基準に PSNR)

480×270、基本シーン(`measurements/capture-480x270.json`):

| 条件 | 秒/枚 | PSNR (dB) |
| --- | --- | --- |
| 16spp デノイズ | 0.78 | 49.2 |
| 16spp デノイズなし | 0.21 | 47.0 |
| 32spp デノイズ | 0.98 | 52.4 |
| 32spp なし | 0.46 | 50.9 |
| 64spp デノイズ | 1.40 | 55.4 |
| 64spp なし | 0.91 | 54.3 |
| 128spp デノイズ | 1.68 | 57.7 |
| 128spp なし | 1.12 | 56.6 |

この小さな画像ではデノイズの固定コスト(約0.55 s)が大きく、**同じ時間なら「デノイズなし・高サンプル」のほうが良い**(例: 0.91 s のなし64spp 54.3 dB > 0.78 s のデノイズ16spp 49.2 dB)。

1920×1080、`--busy-scale 1.35` のシーン(4枚、512→256spp 基準、`measurements/capture-1080p.json`):

| 条件 | 秒/枚 | PSNR (dB) |
| --- | --- | --- |
| 16spp デノイズ | 15.4 | 54.8 |
| 16spp なし | 6.5 | 50.2 |
| 32spp デノイズ | 23.6 | 57.8 |
| 32spp なし | 13.0 | 53.6 |
| 64spp デノイズ | 34.8 | 60.2 |
| 64spp なし | 25.1 | 56.8 |

1080p ではデノイズ固定コストが約 9 s/枚。**同じ時間でみるとデノイズ付きのほうがやや良い**(なし32spp 13.0 s/53.6 dB、デノイズ16spp 15.4 s/54.8 dB。なし64spp 25.1 s/56.8 dB に対しデノイズ32spp 23.6 s/57.8 dB)。基準がデノイズ済みなので、デノイズ側に有利な指標である点に注意。EXR 容量は条件でほぼ変わらない(1.28〜1.36 MB)。

→ 暫定: **1080p はデノイズ付き 16〜32spp**。実作品で再測定(被写体のサンプル当たりコストが大きいほどデノイズ有利)。

### 2.3 シード方針(DD38)

480×270、16spp、θ を 1° ずつ動かした連続6枚、基準=512spp:

| | フレーム間差 RMS(8bit) | 隣接フレームの残差相関 |
| --- | --- | --- |
| ノイズなし(基準。被写体の動きだけ) | 1.43 | — |
| fixed | 1.64 (+0.20) | 0.78 |
| per-frame | 2.15 (+0.72) | 0.04 |
| デノイズ後 fixed / per-frame | 1.55 / 1.83 | 0.76 / 0.15 |

per-frame はスクラブ時のノイズ由来のちらつきが約3.5倍。**fixed を既定のまま維持**。(ノイズ量自体は同じ: 残差 RMS 1.153 / 1.155。)

### 2.4 `use_persistent_data`

| 条件 | persistent あり | なし | 差 |
| --- | --- | --- | --- |
| 480×270, 16spp, デノイズ | 0.78 s | 0.94 s | 約 17% 短縮 |
| 480×270, 64spp, デノイズ | 1.40 s | 1.64 s | 約 15% 短縮 |

固定コスト(シーン読込み・BVH)が小さいほど効くので、**重いシーン・1080p では相対的な効果は小さいはず**(1080p では未測定)。既定は ON のまま。

### 2.5 GPU

**未検証**。この環境に GPU が無い。`--device GPU` は GPU が見つからなければエラーで止まる(DD37。自動テスト済み)。GPU 実測はユーザー側の環境で `--device GPU` を使い、`render_meta.json` の `settings.gpu_devices` を確認すること。

## 3. パック(DD34, DD35, DD39, DD41)

### 3.1 alpha: straight か premultiplied か(**一番効いた差**)

Chromium で AVIF を実際にデコードし、**意図した絵**(straight 色を sRGB 空間で背景に合成したもの)との差を、アルファの縁の帯(半透明画素の5px幅)で測定(1080p、q60、4:2:0、4枚。`measurements/premult-chromium-avif-*.json`):

| AVIF に入れる alpha | 全体 PSNR (白/灰背景) | **縁の帯 PSNR** | 最大誤差 |
| --- | --- | --- | --- |
| premultiplied | 46.0 / 46.0 | **25.6 / 25.6** | 83 |
| **straight** | 54.3 / 54.5 | **39.0 / 39.7** | 44 |

premultiplied は α≈0 の画素に量子化誤差が出ると色が飛ぶ(元 `[0 0 0 0]` → 復号 `[255 0 0 1]`)。暗い背景では明るい点として見える。→ **DD34: straight を既定**。

### 3.2 `premultiplyAlpha` 3種(DD35)

`createImageBitmap` の `premultiply` / `none` / `default` と `ImageDecoder` は、canvas に合成した結果が事実上同一(白/灰背景とも PSNR 差 0.1 dB 以内、最大誤差同じ)。見た目で選ぶ理由はない。既定の `premultiply` のまま。

### 3.3 AVIF 設定(straight、1080p、12枚)

基本シーン(被写体 約10%)と重いシーン(約33%、高周波テクスチャ):

| シーン | quality | speed | chroma | KB/枚 | エンコード s | 全体 PSNR | 縁(白) PSNR |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 基本 | 40 | 6 | 4:2:0 | 8.6 | 0.15 | 49.4 | 35.6 |
| 基本 | 60 | 6 | 4:2:0 | 12.2 | 0.15 | 51.8 | 39.1 |
| 基本 | 80 | 6 | 4:2:0 | 16.9 | 0.14 | 52.7 | 40.9 |
| 基本 | 60 | 6 | 4:4:4 | 12.6 | 0.20 | 55.6 | 41.0 |
| 基本 | 60 | 4 / 8 | 4:2:0 | 11.2 / 13.4 | 0.71 / 0.06 | 51.9 / 51.3 | 39.3 / 38.2 |
| 重い | 40 | 6 | 4:2:0 | 20.9 | 0.18 | 45.3 | 35.4 |
| 重い | 60 | 6 | 4:2:0 | 37.3 | 0.18 | 48.3 | 39.8 |
| 重い | 80 | 6 | 4:2:0 | 60.7 | 0.21 | 49.9 | 42.4 |
| 重い | 60 | 6 | 4:4:4 | 38.2 | 0.26 | 49.5 | 40.5 |
| 重い | 60 | 4 / 8 | 4:2:0 | 36.0 / 47.0 | 1.00 / 0.07 | 48.4 / 46.2 | 39.9 / 38.7 |

- **4:2:0 と 4:4:4**: この2シーンでは 4:4:4 のサイズ増は +3% / +2% で、縁 +0.7〜1.9 dB、全体 +1.2〜3.8 dB。デコードは約12%遅い(`createImageBitmap` p50 22.6 → 25.4 ms、デスクトップ)。ただし**どちらの被写体も色の変化がなめらか**で、実際の素材(細かい色柄)では 4:4:4 のサイズ増はもっと大きいはず。また、Android のハードウェアデコーダが 4:4:4 を扱えず、ソフトウェア復号に落ちる可能性がある(未確認)。→ **既定は 4:2:0 のまま**。実素材と Android で再確認。
- **speed**: 4 はエンコードが 4〜5倍遅く、サイズは 3〜8% 減るだけ。8 は 10〜26% 大きく、画質も落ちる。6 を維持。
- **quality**: 40→60 で +42〜78% サイズ、縁 +3.5〜4.4 dB。60→80 でさらに +38〜63%、縁 +1.8〜2.6 dB。60 を維持(縁の画質が 39 dB 台)。
- **bleed(DD39)**: α=0 の画素に縁の色を広げる(4:2:0、q60)。2px で縁 +1.8 dB だが +14% サイズ、4px 以上は効果なしでサイズだけ増える。4:4:4 ではほぼ効果なし。既定は 0。
- **低解像度ノード画像**(480 幅、q60): 基本 4.2 KB / 重い 8.0 KB(108枚で 0.45 / 0.87 MB)。

### 3.4 総容量(5,928枚 + 低解像度108枚)の見積り(q60, 4:2:0, straight)

| | KB/枚 | 5,928枚 |
| --- | --- | --- |
| 基本シーン(被写体 約10%) | 12.2 | 約 72 MB |
| 重いシーン(約33%、細かい模様) | 37.3 | 約 221 MB |

実作品はこれを上回りうる(細かい色柄が多いほど増える。上の2シーンの差が 3倍あることからも、素材依存が大きい)。**実作品のテスト撮影を `--partial` でパックし、KB/枚 × 5,928 で見積り直す**こと。

## 4. ビューア(Chromium、デスクトップ。Android ではない)

縮小グラフ(60°・15°刻み・×、30ノード・78エッジ、168枚、1920×1080、AVIF 28 KB/枚)をパックして配信、`?dbg=1&bench=1` の**スクリプト操作**(同じ道を決まった速度で動かす。`viewer/packages/app/src/bench.ts`)で計測。生データ `measurements/chromium-*.json`。

### 4.1 デコード方式(1080p、AVIF 11.6 KB の4枚×30回、デコードだけ)

| | p50 | p95 |
| --- | --- | --- |
| `createImageBitmap` 4:2:0 | 22.6 ms | 31.7 ms |
| `createImageBitmap` 4:4:4 | 25.4 ms | 48.1 ms |
| `ImageDecoder` 4:2:0 | 99.7 ms | 130.1 ms |
| `ImageDecoder` 4:4:4 | 116.3 ms | 135.5 ms |

スクリプト操作中の実測(速度 400 px/s、制限なし): `createImageBitmap` は入力→表示遅延 p50 17.5 ms(= 1 vsync)、`ImageDecoder` は 37.5 ms(p95 70.8 ms)。→ **`createImageBitmap` を既定のまま**(DD32、DD42)。

### 4.2 速度・メモリ・キャッシュ(**エミュレーション**: CPU 4倍遅、20 Mbps・RTT 40 ms。実機の代わりにはならない)

| ドラッグ速度 | 制限なし ヒット率 / 遅延p95 | エミュレーション ヒット率 / 遅延p95 |
| --- | --- | --- |
| 400 px/s | 100% / 19.8 ms | 100% / 28.9 ms |
| 1,200 px/s | 100% / 20.9 ms | 89% / 44.9 ms |
| 2,400 px/s | 94% / 21.5 ms | 77% / 64.5 ms |

エミュレーション・1,200 px/s での設定比較(`concurrency` は3回ずつ再測定):

| 設定 | ヒット率 | 遅延 p95 | デコード済み(推定) |
| --- | --- | --- | --- |
| `concurrency` 2(3回) | 90 / 92 / 92% | 35.5 / 31.5 / 27.2 ms | 380 MB |
| `concurrency` 6(既定、3回) | 89 / 90 / 89% | 52.4 / 48.5 / 46.5 ms | 380 MB |
| `cacheMax` 12 | 64% | 55.8 ms | 95 MB |
| `cacheMax` 24 | 67% | 59.6 ms | 190 MB |
| `cacheMax` 48(既定) | 87% | 48.4 ms | 380 MB |
| `cacheMax` 96 | 95% | 26.7 ms | 664 MB |
| `budget` 6 / 10 / 16(既定) / 32 | 90 / 92 / 88 / 92% | 28.9 / 43.5 / 46.3 / 45.3 ms | — |

- **デコード済みフレームのメモリ**: 1920×1080×4 = 約 7.9 MB/枚。`cacheMax` 48 で約 380 MB。JS ヒープ(HUD の heap)にはこれが入らず 3〜4 MB しか出ないので、HUD の `decoded` 行(推定)を見ること。**Android の上限がここで決まる**。実機で `cacheMax` を下げて試すこと。
- **`concurrency`**: この CPU 4倍遅エミュレーションでは 2〜4 のほうが 6 より遅延 p95 が低く、ヒット率は同等。デコードが CPU を取り合うため。ただしフレームが小さく(28 KB)通信が支配的でない条件。実機の通信と CPU で再測定してから既定を変える(今は 6 のまま)。
- **`cacheMax` の下限**: 12〜24 ではヒット率が 64〜67% に落ちる(1,200 px/s)。メモリ制約で絞るなら、速度とのトレードオフを実機で確認。
- `budget`: この範囲(6〜32)では有意な差なし(ばらつきの範囲)。既定のまま。
