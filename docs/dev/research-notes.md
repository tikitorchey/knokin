# リサーチノート(開発の経緯・課題・発見)

各システムの**現在の姿**は `system-*.md`。ここには、そこに至るまでの経緯、直面した課題と選んだアプローチ、**あとから効いてくる注意点**を書く。決定の一覧は [decisions.md](decisions.md)、数値は [measurements.md](measurements.md)。

対象期間: 前任(セッション1〜5。机上テストと合成データ)と、今回(セッション6。実 Cycles・実デコードでの実測)。

---

## 1. 出発点と制約

- 目的: プリレンダリング式の 3D モデルビューア試作機(Knokin Turn Table)。事前に Blender で球面状に撮った画像を、ドラッグ操作で連続的に切り替えて見せる。対象は Chrome(PC / Android)。
- 前任の成果: 「撮影 → パック → ビューア」を、机上テストと合成データで一通り実装。**実際の Blender・実機での値は未決**。
- 今回の環境の制約: Blender 本体なし(GUI なし)、GPU なし、CPU 4 コア・RAM 15 GB、Android 端末なし、コンテナは使い捨て(`/tmp` は消える)、外向き通信は制限つき、コネクタは未接続。
- 方針: **測れないものは推測で埋めない**。測れる範囲は規模を落として実測し、測れないものは手順書と計測の入口を残す。

## 2. テスト戦略: 規模の落とし方

本番(5,928 枚 × 1920×1080)は、この環境で約 26 時間(基本シーン)〜49 時間(重いシーン)かかる。**目的ごとに規模を変えた**。

| 目的 | 規模 | 理由 |
| --- | --- | --- |
| 座標の向き | 480×270、8 視点 | 向きの確認に解像度は不要 |
| サンプル数・デノイズ・シード | 480×270(12 枚)と 1080p(4 枚) | 同じ枚数を全条件で撮って比較する。小さい画像は速いが固定コスト(デノイズ)の比率が歪むので、1080p でも確認 |
| 実規模の撮影コスト | **本番グラフから 100 枚抽出**、1080p | 本番と同じ解像度での 1 枚の時間・容量が取れ、5,928 枚へ換算できる |
| パック品質 | 上の 100 枚(+ 重いシーン 12 枚) | AVIF 設定、縁の品質、容量 |
| ビューアの操作 | **縮小グラフを全部**(60°・15°刻み・×、168 枚、1080p) | 辺をたどる操作はグラフが閉じている必要がある。枚数だけ減らし、構造は本番と同じ |

**教訓**: 辺の途中が欠ける `--partial`(抽出撮影)の出力は、容量・画質の計測には使えるが、ビューアでの操作確認には使えない。

## 3. 実 Cycles の入手: `pip install bpy`

Blender 本体が無くても、`pip install bpy==5.2.2` で Cycles + OIDN が動く。`run_capture.py` は Blender 本体の `-b -P` を前提にしていたので、`bpy` モジュールで動かすために `--blend`(`.blend` を開く引数)を足した。

注意点:
- 起動時の `CUEW initialization failed: Error opening the library` は、CUDA ライブラリが無いという表示で、CPU 撮影では無害。
- `Material.use_nodes` などの Deprecation 警告(Blender 6.0 で削除予定)が出る。テストシーンの作成スクリプトで使っている。
- ベンチは設定ごとにプロセスを分けて、Cycles の状態を毎回きれいにした。

## 4. 座標の向き(DD04 / DD40)

非対称なテストシーン(赤 +X、緑 +Y、青 +Z、黄の鼻 -Y)を作り、実カメラ経路(`place_camera` → Cycles)で 8 視点を描いて目視した。仕様どおり(θ=0 でカメラは -Y 側、θ=90 で +X 側、φ 正で見下ろし)。**対称な被写体(球など)では向きの誤りに気づけない**ので、非対称・色分けのテストシーンが要る。

**構図の失敗**: 最初のテストシーンは、仕様の例(焦点距離 85mm・距離 3.0)では被写体が画面に収まらなかった。テスト用の既定を 50mm・距離 5.5 に変更した。実作品でも、**全視点で枠に収まるか**は撮影前に目視で確認すること(φ±60° で被写体の最大半径が縦方向に出るため、余裕を見る)。

## 5. 影キャッチャーと背景透過(D03 → DD36)

Cycles のシャドウキャッチャー(地面の平面)を試したところ、φ ≥ 0(カメラが地面より上)では接地影が出るが、**φ < 0(カメラが地面の下)では地面が不透明物として被写体を隠し、画像が空になる**。φ±60° の仕様と両立しない。

選択: 影キャッチャーは使わない。背景は透明のまま(影なし)。接地影が欲しい作品は、φ ≥ 0 の範囲に限って別レイヤーとして後日検討する。

## 6. GPU 指定が黙って CPU になっていた(DD37)

前任の実装は `cycles.device = 'GPU'` を設定するだけで、Cycles の環境設定(`compute_device_type`、各デバイスの `use`)を触っていなかった。この場合 Blender は **エラーを出さず CPU でレンダーを続ける**。5,928 枚の本番では数十倍遅くなる事故になる。

選択: `enable_gpu()` を実装し、バックエンドを順に探して GPU だけを有効にする。**見つからなければエラーで止める**。使ったデバイスは `render_meta.json` に残す。実 GPU が無いため、エラー経路のみ自動テストし、**実 GPU での動作は未検証**。

## 7. 撮影条件の比較

### サンプル数とデノイズ
- 480×270(単純シーン): デノイズの固定コスト(約 0.55 s)が支配的で、**同じ時間なら「デノイズなし・高サンプル」のほうが良い**。
- 1080p(テクスチャつきの重め): デノイズの固定コストは約 9 s/枚。**同じ時間ならデノイズ付きがやや良い**(なし 32spp 13.0 s / 53.6 dB、デノイズ 16spp 15.4 s / 54.8 dB)。
- つまり**解像度とシーンで結論が逆転しうる**。実作品で再測定する。PSNR の基準が「デノイズ済みの高サンプル」なので、デノイズ側に有利な指標である点に注意。

### シード方式
`fixed` は隣接フレームのノイズが相関する(0.78)ので、スクラブ中に「窓に付いた汚れ」のように静的に見え、ちらつきが小さい。`per-frame` は無相関(0.04)でちらつきが約 3.5 倍(基準に対する超過分 +0.72 対 +0.20)。ノイズ量そのものは同じ。→ fixed を既定のまま維持。

### `use_persistent_data`
480×270 では約 15〜17% 短縮。固定コストが小さいほど相対効果は小さくなるはずなので、1080p・重いシーンでは効果が薄い見込み(**1080p は未測定**)。

## 8. パックの品質: 一番大きな発見(DD34)

### 経緯
最初の `bench_pack.py` で縁の PSNR が 11〜15 dB と異常に低かった。原因を追った。

1. Pillow のデコード結果は「乗算済み規約」のままで、比較側の規約は合っていた(取り違えではない)。
2. 画素を見ると、元が `[0 0 0 0](完全透明)`の位置が、復号後に `[255 0 0 1]` などになっていた。

### 原因
乗算済み(premultiplied)の画像は「色 ≤ α」を前提にする。AVIF の量子化誤差が α≈0 の画素の色に乗ると、**色が α を大きく超える**。乗算済みとして合成すると、暗い背景の上で明るい点(ハロー)になる。straight(非乗算)なら、α≈0 の画素の色は表示にほぼ効かない。

### 検証
Chromium の実デコードで、「意図した絵」(straight 色を sRGB 空間で背景に合成したもの)との差を、アルファの縁の帯で測定:

| | 縁の帯 PSNR | 最大誤差 |
| --- | --- | --- |
| premultiplied で AVIF 化 | 25.6 dB | 83 |
| straight で AVIF 化 | 39.0 dB | 44 |

→ `image.alpha` は新規撮影で `straight`。パッカーは premultiplied だと警告する。

### 追加で試したが採用しなかったもの
- **bleed**(α=0 の画素に縁の色を広げる): 4:2:0 で縁 +1.8 dB、サイズ +14%。それ以上は効果なしでサイズだけ増える。割に合わず、オプションとして残して既定 OFF(DD39)。
- **4:4:4**: この 2 シーンでは +2〜3% のサイズで縁 +0.7〜1.9 dB。ただし素材が単純(なめらかな色)なので一般化できず、デコードも +12%、Android のハードウェアデコーダの対応も未確認。→ 4:2:0 を維持(DD41)。

### `premultiplyAlpha` の3モード
`createImageBitmap` の 3 モードと `ImageDecoder` は、canvas に合成した結果が同一(PSNR 差 0.1 dB 以内)。**見た目で選ぶ理由はない**。→ 既定の `premultiply` のまま。

### 注意
- 容量は被写体で大きく変わる(基本シーン 12 KB/枚、重いシーン 37 KB/枚)。5,928 枚で 72〜221 MB という見積りは、**この 2 シーンに限る下限寄りの値**。実作品でテスト撮影して見積り直す。
- パッカーが `render.pack` に `bleed` を記録していなかったので、ドキュメント整理の際に追加した。

## 9. ビューアの計測

### 道具の設計
実機で「どの設定で測ったか」を URL で再現でき、指で操作せず比較できるよう、次を用意した(DD43)。
- スクリプト操作(同じ道を同じ速度で再生)、URL パラメータ、JSON をテキスト欄にも出す(LAN の http ではクリップボード API が使えず、スマホではダウンロードも扱いにくいため)。
- Playwright の計測スクリプト。`CPU_SLOWDOWN` / `NET` でエミュレーション。

### 分かったこと
- `createImageBitmap` は `ImageDecoder` より約 4 倍速い(デコードのみ 22.6 ms 対 99.7 ms)。→ 既定のまま(DD42)。
- 入力→表示の遅延 p50 17.5 ms は **1 vsync 分**で、ヒットしているときの下限。**実機の遅延ではない**。
- 高速ドラッグ(2,400 px/s)と CPU 4 倍遅・20 Mbps のエミュレーションで、ヒット率が 77% まで落ちた。
- `concurrency` は、CPU 4 倍遅のエミュレーションでは 2〜4 が 6 より遅延 p95 が低い(デコードが CPU を取り合う)。ただしフレームが小さく(28 KB)通信が支配的でない条件なので、既定は変えず、実機で再測定する。
- キャッシュ上限を 12〜24 に絞るとヒット率が 64〜67% に落ちる。

### メモリが最大の不確実要素
デコード済みの 1080p は約 7.9 MB/枚で、`cacheMax` 48 で約 380 MB。**JS ヒープ(`performance.memory.usedJSHeapSize`)にはこれが入らない**(3〜4 MB のまま)。HUD に「デコード済み推定 MB」を足して、これを見られるようにした。Android でタブが落ちる境目は実機で探す必要がある。

## 10. 誤りと教訓(再発防止)

| 事象 | 影響 | 教訓 |
| --- | --- | --- |
| 縮小グラフの manifest を、alpha 既定を変える**前**に作った | 数枚撮ったところで気づいて撮り直し | 撮影前に manifest の `image.alpha` を確認。`m_view.json` のように長い撮影は、開始前に出力設定を点検する |
| ビューアの速度スイープが、**ビルド失敗のまま古いバンドルで走った** | 速度パラメータが効かず、全条件で同じ値が出た | `npm run build` の終了コードを必ず確認する。結果が条件に依らず同じなら疑う |
| `pkill -f "<パターン>"` が**自分のシェル**のコマンドラインにも一致して、実行中のシェルごと落ちた(2 回) | サーバ・撮影が止まった | プロセスは PID で止める。常駐させるものは `setsid nohup … & disown` で別セッションにする |
| `vite preview` をルート(`viewer/`)で起動したら 404 | 計測が始まらなかった | `viewer/packages/app` で起動する(`dist` がそこにある) |
| 最初のテストシーンが構図に収まらなかった | 向きの確認画像が役に立たなかった | 構図(焦点距離・距離)も撮影前の確認項目に入れる |

## 11. 未解決・今後の課題

- **Android 実機**: 遅延、取得・デコード時間、ヒット率、メモリ、`ImageDecoder` の速度、`maxItems` / `concurrency` / `budget` の調整。→ `android-measurement.md`
- **操作感**: `degPerPx` `turnPx` `deadZoneDeg` `stickyDeg` は仮置きのまま。実機で触って決める。
- **GPU 撮影**: 実 GPU での動作・速度。`enable_gpu()` は未検証。
- **実作品**: サンプル数、撮影時間、EXR/AVIF 容量。テスト 2 シーンは単純で、数値の一般化はできない。
- **4:4:4**: 実素材と Android のハードウェアデコーダで再確認。
- **未実装**: `diagonals: "alternate"`、重点エリア用の `span`/`stride`、`render.capture` の項目確定(現状は `render_meta.json` をそのまま取り込む)。
- **エッジ途中の代役画像**: ノードにしか低解像度が無く、辺の途中でフル画像が遅れると直前のフレームが残るだけ。実機で目立つか確認。
- **データの保存**: 撮影画像は git に入れない。実作品の EXR(数 GB〜十数 GB)は外部ストレージ(Google Drive を想定。コネクタは新しいセッションで接続が必要で、大きいファイルを送れるかは未確認)に置く。今回のテスト資産は破棄した。
